# DD-043 PR-4 — the Tomcat 0.8.15 coverage-path regression run, actually run (F2)

**Verdict: the run COMPLETED.** The runner's live Tomcat tcpserver coverage path
(`runner/coverage/JacocoCoverageProvider.java`) was re-run against a real Tomcat 9 JVM carrying the
staged JaCoCo **0.8.15** agent, against the real JPetStore-6 WAR, over three samples spanning two
route-driving rounds. Every class supplied was analyzed (**24/24, 0 skipped**) at every sample, and
covered instructions grew **33 → 141 → 605** (out of a constant 2124 total probes) as routes were
driven. No skip, no zero-of-zero, no fabricated number: every figure below is quoted from a file in
`logs/` committed alongside this README, generated by the commands shown.

This closes approver finding F2 on PR #110: the PR body's Tomcat-guard claim ("24/24 classes,
coverage grew") traced to no committed byte. It now traces to this directory. The PR body's exact
"24/24" wording turns out to be numerically accurate — but that was NOT known when this directory was
started; it is a coincidence confirmed by measurement, not a number carried over from the PR body.

## What was run and why

Plan `docs/superpowers/plans/2026-08-10-dd043-pr4-coverage.md` Task 3 requires "a real Tomcat
coverage-path run under 0.8.15" as D1's bump behaviour-preserving guard, because the staged-agent-jar
path (`build.gradle:433`, `build.gradle:444`) is mounted into a live Tomcat JVM and driven by nothing
in the unit suite. This directory is that run, executed fresh for this fix (the earlier PR-4 work
apparently ran it once, interactively, without committing any record — this run replaces that with a
committed one).

## Recipe (exact commands run, in order)

Base: `git fetch origin && git reset --hard origin/dd043-pr4-coverage` — HEAD

**1. Confirm the shared version property** (`gradle.properties:15`): `jacocoVersion=0.8.15`.

**2. Build the JPetStore-6 WAR** — cloned fresh to a scratch directory outside this repo:

```
git clone --depth 1 https://github.com/mybatis/jpetstore-6.git
cd jpetstore-6   # HEAD 6b0ac6a02aa7ccc530d3231506a95999bbc04810, 2026-08-09 (logs/jpetstore-commit.txt)
mvn -DskipTests -Denforcer.skip=true -Dmaven.gitcommitid.skip=true package
```

**Disclosed deviation**: this environment's system Maven is 3.6.3. JPetStore's
`git-commit-id-maven-plugin:10.0.0` requires Maven `[3.9.0,)`, and the system `mvn` command above
failed immediately with exactly that message — "requires Maven version [3.9.0,)" — before any
compilation started (not saved to `logs/`: it produced no artifact, only a one-line rejection, so
there is nothing to commit beyond disclosing it here). JPetStore ships its own wrapper pinned to
Maven 3.9.16 (its `distributionUrl` property, in the wrapper properties file the JPetStore-6 clone
ships under its own dot-mvn wrapper directory — external to this repo, not cited by path here), so
the command
actually captured in `logs/jpetstore-maven-build.log` is the project's own `./mvnw` with the same
skip flags:

```
./mvnw -DskipTests -Denforcer.skip=true -Dmaven.gitcommitid.skip=true package
```

`BUILD SUCCESS` (`logs/jpetstore-maven-build.log:290`), producing an 11,988,631-byte
`jpetstore.war` (`logs/jpetstore-war-ls.txt`) with 24 `org/mybatis/jpetstore/**/*.class` entries
(`logs/jpetstore-war-classlist.txt`, 24 lines) — an in-memory-HSQLDB WAR needing no external DB, per
`docs/THIRD-PARTY-APPS.md`'s existing JPetStore recipe. This is a build-tooling substitution only:
the WAR that came out is the same artifact the documented recipe describes, still produced by
`mvn package` with the same three skip flags, just invoked through the project's own wrapper because
the system-wide Maven predates what this specific upstream plugin version demands.

**3. Stage the agents** (`./gradlew stageAgents`, `logs/stageAgents.log:27` `BUILD SUCCESSFUL`) and

## Result

| Sample | Trigger | covered | total | classesAnalyzed | classesSkipped | sourcesResponded/Total |
|---|---|---:|---:|---:|---:|---:|
| t0 | container start, no routes driven | 33 | 2124 | 24 | 0 | 1/1 |
| t1 | round A (7 routes) | 141 | 2124 | 24 | 0 | 1/1 |
| t2 | round B (13 routes) | 605 | 2124 | 24 | 0 | 1/1 |

**24/24 classes analyzed, 0 skipped, at every sample; coverage grew monotonically across both drive
rounds (33 → 141 → 605).** The JaCoCo 0.8.15 bump does not break the staged-agent-jar → live-Tomcat
path: D1's loud-skip guard (`runner/coverage/JacocoCoverageProvider.java:200`) never had anything to
report skipped, because 0.8.15's analyzer parsed every one of JPetStore's real (much older,
non-Java-25) classfiles cleanly — this run doesn't exercise the Java-25-classfile hazard D1 was
written for (that hazard is native/JVM-25 target-specific, per PR-4's Task 4 acceptance in
`bench-results/dd043-pr4-2x2-2026-08-10/`), but it does prove the OTHER thing Task 3 needed proved:
the version bump did not regress the tcpserver-over-a-live-Tomcat-JVM transport itself.
