## What it delivers
Offline-JaCoCo coverage for an app instrumented at build time by `basquin-maven-injector`, no source
edits: the injector adds a jacoco `instrument` execution, the `basquin-quarkus` extension serves the
execution data at `/__basquin/coverage`, the runner reads it over HTTP. Acceptance = the native **2×2**
(rest-villains × rest-heroes, JVM × native) inject+read cell, end-to-end.

## Locked decisions
- **A1 — jacoco-runtime-dep channel = the extension's pom (not a 4th injector mutation).**
  `basquin-quarkus/runtime` declares `org.jacoco:org.jacoco.agent:<ver>:runtime` as `implementation`.
  Fable confirmed both halves: (a) it lands on the extension's compileClasspath so §6.4's typed
  `RT.getAgent().getExecutionData(false)` read compiles; (b) the runtime module publishes via plain
  `from components.java`, so the dep lands as ordinary `<scope>runtime</scope>` and propagates to the
  target transitively through the already-injected `basquin-quarkus` — runtime scope suffices (the
  app's instrumented classes need `Offline` at run/link time only), and Quarkus feeds it to both
  packaging and `native-image` (`--link-at-build-time` would fail LOUDLY if it were missing). A1 wins
  on its real merits — **one channel, no new injected-artifact guard surface, and version lockstep with
  the RT read** — and safely: `failOnConflictingDeclaredVersion` forces the already-declares path to
  resolve the PR-4 pom (jacoco-carrying), never a pre-PR-4 one.
- **Version lockstep (new, from review issue 3).** JaCoCo version lives in ONE shared Gradle property
  (`gradle.properties`/root `ext`, replacing the script-local `def jacocoVersion` at `build.gradle:35`)
  consumed by the runner bump AND the extension dep. The injector's injected version is a **Java
  constant that cannot read a Gradle property** → generate it via the repo's existing
  `InjectorVersion.value()` generated-source pattern (or, at minimum, a test/harness row asserting
  injector-constant == extension-dep == runner-pin). Drift is not cosmetic: offline-instrumented
  classes reference the version-specific shaded package (`org.jacoco.agent.rt.internal_<hash>`), so
  plugin-vs-agent skew breaks the read at runtime. **jacoco-cli (Tasks 0, 5) is pinned to the same
  version** — a 0.8.12-era cli hits the same Java-25 ASM wall.
- **D1 — bump JaCoCo `0.8.12 → 0.8.15` and make the skip LOUD.** 0.8.12's ASM cannot parse the
  targets' Java-25 (major-69) classfiles and `analyzeClass` swallows the exception → a silent-zero
  denominator (the cardinal defect). Count skipped classes, surface the count in `Coverage`, FAIL when
  all classes skip. **The bump's Tomcat guard is a REAL run, not the unit suite** (review issue 2): the
  agent jar is consumed by `copyJacocoAgent`/staging and mounted into a live Tomcat JVM
  (`build.gradle:429-444`) — a path no unit test drives — so Task 3 runs the actual Tomcat coverage
  path once under 0.8.15 and asserts it still produces coverage.
- **D2 — injector fails LOUDLY on a conflicting jacoco declaration** (matching §5.1 / the `failOn*`
  guards), with a mutation row in `scripts/verify-dd043-pr3.sh`. Define "conflicting" precisely: an
  **active** `jacoco-maven-plugin` `instrument`-execution or a version collision (a target's own
  `prepare-agent` is not in itself the conflict); profiles are already merged into the effective model
  by `afterProjectsRead`, so the targets' inactive `it-coverage` jacoco is invisible and acceptance
  builds don't collide. The guard message names the existing `basquin.inject.skip` escape hatch.
- **RT-unavailable → a distinct non-2xx, never an empty-but-200 body** (an empty 200 is a manufactured
  "zero coverage").
- **Mode recorded in every coverage artifact; NO cross-mode percentage anywhere** (§6.4/§7.4: native's
  denominator includes reachability-eliminated code). PR-4 keeps guidance within one mode and does not
  pre-empt PR-5's §7.4 rendering.
